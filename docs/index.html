System design: the drawboard

The main PC hosts, the STRIX laptop joins. Nobody uses Hamachi or ZeroTier: PrivCord's own peer-to-peer tunnel carries the game traffic, so each player's mod simply connects to 127.0.0.1:5050 on their own machine.

Port map: 5050 = the mod's dedicated server (the only stream that needed framing), 5051 = PrivCord party feed (who's in, hearts, distance, teleports), 5053 = downed/revive relay. On the friend's PC, 5051 and 5053 go to any free local port so a busy port can't break a join.

How both players see each other in real time

One position update, start to finish, from Kev's Link on STRIX to Kev's puppet on the main PC. The same trip runs in the other direction at the same time.

Why it's “real time”

  • The server is strictly request/response: every client update gets an immediate snapshot back, so there is no server tick to wait for.
  • The DLL writes the puppet's position every 16 ms (one 60 fps frame), extrapolating with the last velocity.
  • The tunnel ran Direct · 6 ms between the two PCs on the LAN.
  • The map shows every other player as a live marker with their name; “HP: n” appears when close. That comes from the mod, we built nothing for it.

What made it look choppy (and the fix)

  • STRIX is on Wi-Fi, which batches packets: updates arrived 20 ms apart, then 36–40 ms late, then two at once (~4 ms).
  • A late update means a frozen puppet; a late pair means a jump. 14% of frames were frozen.
  • Fix: a jitter buffer next to the game. No game patch, no DLL change. It reads what the DLL received and writes a smoothed position right after each DLL write.
  • Result: 0% frozen frames, step p90 0.22 → 0.137 m.

The chain we had to measure, link by link, to get here

split message→ server drops Kev's updates→ Updated flag never set (0 of 227,150)→ host DLL's copy of Kev stays (0,0,0)→ PThread writes (0,0,0) into the puppet at ~233 ms→ game's “fell out of the world” check (20 m)→ requestDelete → deleteLater→ OnActorErase→ DLL respawns 3 s later: ghost loop

We started at the end of that chain and walked backwards. The step that broke it open: attaching as a debugger and putting a hardware write breakpoint on the puppet's Havok motion state (watch-writer.ps1). Until ~227 ms only game code wrote there; from ~233 ms it was InjectDLL+0x3a3b2 writing zeros. So the game wasn't killing the puppet, the mod was feeding it a zero position. From there players2.py showed the DLL's cached position for Kev never changed, and a logging proxy (proxy.py on port 5051 → 5050) showed the server never sent Updated = 1. The server log's [Kev] Retried N times (45×) was the last clue: the server was choking on Kev's messages.

The original PointCrow mod vs the PrivCord way

BOTW Multiplayer 1.0.4 was made by the team around PointCrow (lead dev MadMilkman) and taken down after Nintendo takedowns, so 1.0.4 is final and nobody fixes it any more. We did not change a single byte of it: the server, the injected DLL and the mod's game files are untouched. Everything PrivCord does sits around the mod: how it is installed, launched, connected, configured and extended.

The tutorial way (per player)

  1. Install Hamachi, join the host's network
  2. Install Python + BCML
  3. Merge the mod's BNP files in BCML
  4. Find the right Cemu version (older than 2.0-47)
  5. Dump the game, update v208 and DLC
  6. Install update + DLC into Cemu's storage
  7. Download Extended Memory + FPS++ packs
  8. Enable the right graphic packs
  9. Set up a controller profile
  10. Install the .NET 6 Desktop Runtime
  11. Make a single-player save first
  12. Host: run the server, answer its console prompt
  13. Share your Hamachi IP, friend types it in

The PrivCord way

  1. Install (game, mod, Cemu, packs, settings, profile: all automatic, hash-checked)
  2. Host or Join on the card in chat
▶ playing together

What we had to fix around the mod, sorted by whose problem it was

Bugs in their mod (worked around, can't edit it)

  • Server corrupts messages that arrive split → tunnel framing
  • Server crashes when stdin closes → keep an open pipe
  • Server crashes on connect-then-close (GetPlayer(-1)) → never probe it
  • IP=localhost binds the LAN card → rewrite to 127.0.0.1
  • DLL only scans the 8th memory region → Extended Memory pack always on
  • Flag scan sometimes never finds the map pin (timing) → still flaky, not fixed

Version traps

  • Mod needs Cemu older than 2.0-47 → separate Cemu 1.26.2
  • Utilities pack says version = 7, which 1.26.2 skips silently → our v6 copy
  • New community graphics packs are v7 → pinned to release Github833
  • Official Cemu 2.6 zip has a garbled file name → re-staged without it

Our own bugs

  • Client launched with NUL handles → Cemu 0xc0000409 → ShellExecuteW
  • Readiness probe connected and killed the server → bind check
  • “Cemu.exe” case mismatch → lowercase both
  • Stale downed flag killed both players → ¼-heart check
  • Revive reset on one-tick blips → 0.6 s grace
  • Old join held port 5050 → drop overlapping joins
  • Party feed reply had no size limit → 64 KiB cap

Hardware & environment

  • Wi-Fi bunches packets → jitter buffer
  • WriteProcessMemory 12 ms per call → NtWriteVirtualMemory
  • Cemu controller set to Disabled → Wii U GamePad + key map
  • GUI apps over SSH invisible → schtasks /it
  • STRIX panel reports 60 Hz → High preset at 60 fps

Why this is better than the plain mod

  • It works over a real connection. The plain mod's server drops a joiner's updates whenever messages arrive in pieces. That is what made the ghost Links.
  • Two clicks instead of a 13-step guide, with every package hash-checked and every change to your settings backed up.
  • Safer. The server only listens on loopback, behind a tunnel only room members can use. With Hamachi, anyone on that network could reach it, and one bad connection could crash it.
  • Smoother. The other player no longer freezes and jumps on Wi-Fi.
  • More game. Harder enemies for two players, downed and revive, party HUD, teleport buttons, auto graphics.
  • Repeatable. Install is idempotent and covered by end-to-end tests, so a re-run is a sub-second no-op.

Where we're still limited by the original

  • We still depend on their closed DLL and server. Bugs inside them, like the flaky flag scan, can only be worked around.
  • Locked to old Cemu 1.26.2 and game version v208, Windows only.
  • The wire format is fixed, so new data (items, downed state) has to travel on our own side channels.
  • “Hunter vs Speedrunner” has no rules in 1.0.4; it's just a label.
  • The server supports 32 players; we have only tested 2.

10 · Our own PowerPC patch (downed instead of dead)

Cemu graphic packs can add assembly to the game. This one routes both of Link's health stores through our clamp. Mode 0 (vanilla) is the default, so it does nothing unless PrivCord arms it.

✗ looks right, reads address 4 
; r0 as a base register means literal 0 on PowerPC
li   r0, DownBlock@l
lwz  r9, 4(r0)      ; NOT DownBlock+4 → crash
✓ patch_PrivCordDowned.asm 
DownClamp:
lis  r12, DownBlock@ha
addi r12, r12, DownBlock@l
lwz  r9, 4(r12)     ; DownMode
cmpwi r9, 1
bne  DownClampOut   ; mode 0 or 2: vanilla
lwz  r10, 8(r12)    ; DownState
cmpwi r10, 0
bne  DownHold       ; already downed: hold ¼ heart
cmpwi r3, 0
bgt  DownClampOut   ; survives the hit

What we should have done differently

The fix itself was small: one framing function in the tunnel. Getting to it took three sessions. These are the shortcuts we can see now.

cost us ~2 sessions

Capture the network traffic first

Did: started inside the game, hooking ~35 PowerPC addresses to trace why the puppet was deleted.

Should have: put the logging proxy between client and server on day one. “0 replies with Updated = 1” points straight at the network.

hid the bug

Test the real path early

Did: the install and host tests all ran on one PC, over loopback, where messages never split.

Should have: run one two-PC join through the tunnel before polishing the installer.

cost a session

Follow the mod's guide to the letter, then improve

Did: switched to Cemu 2.6 and decided the extra packs weren't needed.

Should have: copied the guide's exact setup (Cemu 1.26.2, Extended Memory, FPS++), got it working, and only then changed things.

fast to read, slow to find

Read the server's code before the game's

Did: decompiled the .NET server early, but read it for features, not for its receive loop.

Should have: treated “append the whole 10 KB buffer on every read” as a suspect the moment a second PC was involved.

built, then removed

Decide the network first

Did: built the full ZeroTier integration, then made BotW tunnel-only.

Should have: settled “tunnel or virtual LAN?” before writing either.

crashed the server

Never poke a fragile server

Did: a quick “is it up?” connect, which crashed it.

Should have: assumed closed, unmaintained software can't take surprises, and watched it from outside (port bound, log lines).

open question

One save on both PCs

Did: copied the same save to both Cemus to get past the “needs a save” step.

Should have: given each player their own save from the start; how co-op progress should merge is still undecided.

what went right

Measure before fixing

Every real fix came from a number: the write breakpoint, the 0-of-227,150 count, the 20/40/4 ms arrival gaps, the 12 ms write cost. Keep doing that.

Once it worked: co-op add-ons

None of these modify the mod. They use the server's own config file and console, our own graphic packs generated from each player's own game files, and sidecars that read and write Cemu's memory.

What we can do better, and what's next

Effort estimates come from the co-op research plan. The rule for everything new: it travels on PrivCord's own side channel (sidecar + our own patches), never on the mod's fixed wire format.

Now days

Combined build on both PCsCo-op, gameplay and shared-enemies work in one build. Install once, then one full two-player session inside the app.
Shared enemies P3: hitsDamage dealt to a puppet copy goes to the owner's real enemy.
Finish the unverified bitsInput freeze while downed, max graphics in game, smoothing seen from STRIX's side.
Smoothing inside the gameA per-frame PPC hook reads our smoothed position, removing the last spike every ~2 s.
Enemy damage multiplierSecond host setting, rides on the same DownClamp hook.
Auto-install .NET 6 runtimeThe last manual step for friends.
Clean-upRemove the diagnostic trace pack from the main PC; STRIX on Ethernet or Wi-Fi power saving off; check whether its screen can run above 60 Hz.

When to start the DLL rewrite

Not now. Switch only if one of these happens: a feature needs a new field on the mod's wire; the DLL stops working or can't be obtained; we want an installer with no third-party downloads; or a remaining puppet bug can only be fixed inside the DLL.
